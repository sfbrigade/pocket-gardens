## Preserve identities; no registration required

Keep the existing `User` table and **every existing `User.id` UUID**. Add Better Auth fields/tables around those rows; backfill `name` from existing names and retain profile metadata. UUIDs are supported through `advanced.database.generateId: 'uuid'`; that controls new IDs, not a requirement to replace existing IDs. Keep UUID types on `Session.userId` and `Account.userId`. The current `Invite` foreign keys already depend on these IDs. [Official database schema/customization](https://better-auth.com/docs/concepts/database); [current User/Invite schema](/Users/Samau/Desktop/RithmSchool/Studying-Review/pocket-gardens/server/prisma/schema.prisma:16).

Magic-link verification looks up an existing user by email and creates a session for that user's ID. Existing users therefore need a sign-in/verification email, **not a new registration or duplicate User**. Set `disableSignUp: true` for an initial existing-account-only flow, or separately preserve invitation/public-registration admission rules. Default magic-link configuration permits signup for unknown emails. [Magic-link documentation](https://better-auth.com/docs/plugins/magic-link); [lookup/session source](https://github.com/better-auth/better-auth/blob/3fa26c979160914ce8e1c0e8786b1f48aa2552e5/packages/better-auth/src/plugins/magic-link/index.ts#L416).

Do not merge imported volunteer `Person` identities into auth users or infer ownership from contact text. The [existing identity ADR](/Users/Samau/Desktop/RithmSchool/Studying-Review/pocket-gardens/docs/adr/0001-preserve-volunteer-identities.md:1) explicitly preserves those records and defers verified account linking.

## Passwords and verification: a consequential choice

Existing passwords use `bcrypt.hash(password, 10)` / `bcrypt.compare`; Better Auth defaults to scrypt. For each imported password, create a separate Account row with a fresh row UUID, `providerId = 'credential'`, `accountId = User.id` (string), `userId = User.id`, and `password = User.hashedPassword` **unchanged**, with required timestamps. Copying hashes alone is insufficient: configure `emailAndPassword.password.verify({ hash, password })` to recognize legacy bcrypt and call `bcrypt.compare(password, hash)`. [Current bcrypt implementation](/Users/Samau/Desktop/RithmSchool/Studying-Review/pocket-gardens/server/models/user.js:102); [official credential migration requirements](https://better-auth.com/docs/guides/next-auth-migration-guide#comparison); [custom password hashing/verifying](https://better-auth.com/docs/authentication/email-password#configuration).

Implementation options: continue bcrypt for both new hashing and verification initially, or hash new/reset passwords with Better Auth's exported scrypt helper and dispatch verification by a validated hash format. The latter is a design recommendation, not automatic rehash-on-login behavior. Never hash an imported hash as though it were a plaintext password; ensure resets/new passwords and legacy credentials all use compatible paths. [Password helper source](https://github.com/better-auth/better-auth/blob/3fa26c979160914ce8e1c0e8786b1f48aa2552e5/packages/better-auth/src/crypto/password.ts); [sign-in verifier source](https://github.com/better-auth/better-auth/blob/3fa26c979160914ce8e1c0e8786b1f48aa2552e5/packages/better-auth/src/api/routes/sign-in.ts#L535).

**Importing credentials with `emailVerified = false` does not preserve them through first magic-link login.** Current upstream deliberately deletes *all Account links* and existing sessions before marking that account verified. This protects against credentials planted before mailbox ownership was proven. Do not disable that protection or globally mark old emails verified merely because users exist. [Cleanup implementation](https://github.com/better-auth/better-auth/blob/3fa26c979160914ce8e1c0e8786b1f48aa2552e5/packages/better-auth/src/db/revoke-unproven-account-access.ts#L31); [first-party security advisory](https://github.com/better-auth/better-auth/security/advisories/GHSA-qq9h-g4jm-xgf3).

Two supported migration experiences follow:

1. **Retain passwords:** import credential rows and obtain actual email proof first. Standard Better Auth email verification updates `emailVerified` without invoking that magic-link cleanup in the inspected version; complete it before the first magic-link login. Alternatively import verified status only where trustworthy prior verification evidence exists. `requireEmailVerification: true` gates password login until verification. This sequence needs an integration test on the chosen version. [Verification endpoint source](https://github.com/better-auth/better-auth/blob/3fa26c979160914ce8e1c0e8786b1f48aa2552e5/packages/better-auth/src/api/routes/email-verification.ts#L482); [email/password verification docs](https://better-auth.com/docs/authentication/email-password#require-email-verification).
2. **Magic link immediately:** retain User IDs and let the link prove email ownership and sign users in. Unverified legacy credentials will be removed; a later password-reset flow can set a new password. This meets “no re-registration,” but does **not** meet “keep the old password working.” Document that distinction before choosing it. [Magic-link verification behavior](https://better-auth.com/docs/plugins/magic-link#verify-magic-link).

## Sessions and access status

Pocket Gardens uses an encrypted Fastify session containing `userId`; Better Auth uses its own session token/records. Plan a one-time sign-in after cutover rather than promise cookie continuity. Adapt the Fastify request-user bridge and forward all session `Set-Cookie` headers, including refreshes; the sibling demonstrates this integration. Preserve server-side authorization on application routes. [Current session plugin](/Users/Samau/Desktop/RithmSchool/Studying-Review/pocket-gardens/server/plugins/auth.js:8); [reference bridge](/Users/Samau/Desktop/RithmSchool/Studying-Review/resource-binder-server/server/plugins/auth.js:12); [official sessions](https://better-auth.com/docs/concepts/session-management).

Current active status is `!deactivatedAt`, independent of email verification. The sibling maps `isAdmin → role='admin'` and deactivation to `banned=true`, then defines active as `emailVerified && !banned`. Preserve every existing admin/deactivation value and decide explicitly whether to adopt this stronger active definition. Keep privilege fields unavailable to ordinary profile input; Admin plugin endpoints have separate permissions. Disable cookie caching initially, or force fresh server lookups for sensitive checks, so deactivation/demotion is promptly enforced. ## Reference audit: borrow integration, rewrite the data cutover

- The [reference auth migration](/Users/Samau/Desktop/RithmSchool/Studying-Review/resource-binder-server/server/prisma/migrations/20260909000100_better_auth_magic_links/migration.sql:90) preserves User IDs, backfills names/admin/banned status, but **imports no credentials or sessions**. Lines 99–103 drop `hashedPassword`, `isAdmin`, reset fields, and `deactivatedAt`; all old emails start unverified. This is destructive for production password continuity and loses the original deactivation timestamp. Its [own migration notes](/Users/Samau/Desktop/RithmSchool/Studying-Review/resource-binder-server/docs/authentication.md:89) describe a development cutover, not a reversible production migration, and warn about reconciled historical migrations.
- The [later migration](/Users/Samau/Desktop/RithmSchool/Studying-Review/resource-binder-server/server/prisma/migrations/20261029000100_magic_link_registration_fields/migration.sql:1) only adds nullable registration JSON. Its [custom registration wrapper](/Users/Samau/Desktop/RithmSchool/Studying-Review/resource-binder-server/server/lib/auth-magic-registration.js:37) hashes tokens, validates profile/invitation admission, and wraps creation/acceptance in a transaction. It depends on version-specific adapter context and plugin internals; copy only if these registration requirements apply, with focused tests.
- Recommended production migration: additive fields/tables, transactional credential/status backfill, before/after UUID and relationship assertions, no early legacy-column drops. Rehearse restoration plus post-cutover password writes; leaving legacy columns alone does not make rollback automatically correct. For Prisma, Better Auth generates schema; Prisma owns applying reviewed migrations. [Official Prisma adapter workflow](https://better-auth.com/docs/adapters/prisma#schema-generation--migration).
